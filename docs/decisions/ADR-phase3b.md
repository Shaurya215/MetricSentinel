# ADR: Phase 3b - one improvement round on the anomaly detector

* Status: **Accepted. Protocol pre-registered on 2026-10-26, before any 3b code was written or any 3b result existed.**
* Baseline: git tag `phase-3-baseline` (commit `5c385bc`). Run `11147b0`, data hash `8333919867b2`, detector `16cecd334dd9`, scenarios `3fedd09cae9d`.
* Results: **none yet.** This file is extended with harness-generated numbers only (section 14). Nothing below is a result.

## 1. Context

Phase 3 delivered the detector but missed NFR-021: recall 56.2% (9 of 16) on faults of 20% or more, against 80%, and 9.26 false alarms per 30 days, against 2. The gap analysis (`docs/AI_ML_PLAN.md` section 2.5) names causes: the end of the data, the January surge, heavy-tailed GMV, diluted small segments, and slow weekly series.

## 2. Decision

Run **one** time-boxed round of four changes (A to D) plus reporting improvements (E), in this order, each behind a configuration flag and measured separately on 2017 data. Then freeze, and evaluate on 2018 exactly once.

| | Change |
|---|---|
| A | Volume-collapse guard and a "last reliable day" rule; fix the Phase 2 window rule (centred mean) |
| B | Log scale for GMV |
| C | Test a segment's share of its parent total instead of its level (orders and gmv only) |
| D | Calendar windows: tag `calendar_uncertain` and lower severity; never silence |
| E | Recall by segment size with Wilson intervals, an operating curve, false alarms split by cause |

Out of scope: a seller-state dimension, new fault types, new model families, any change to the Phase 3 baseline results.

## 3. Contamination caveat (stated up front)

The 2018 false alarms were diagnosed by hand in Phase 3, and the end-of-August cut-off was seen there. **2018 is therefore not held out.** All development choices use 2017 only. The final 2018 numbers are labelled **"post-diagnosis, not held-out"** everywhere they appear, and are shown next to the baseline, never in place of it. The "last reliable day" rule and the known-events list are *validity rules defined after diagnosis* and are labelled that way.

## 4. Development protocol (2017 only)

* Fit period: 2017-04-26 to 2017-08-27. Model choice and interval calibration for every development configuration use only this period. The Phase 3 detector used all of 2017, so the baseline is **re-fitted on the fit period only** (`baseline-dev`) for a like-for-like comparison.
* Test period: 2017-08-28 to 2017-12-31.
* Clean days: every test-period day outside the Black Friday event (2017-11-23 to 2017-11-29), which is 119 days. Black Friday is excluded for every configuration, so they stay comparable. The Christmas days (from 2017-12-20) **stay in**, because they are the only calendar window D can be observed in. With about 119 days the false-alarm estimate is noisy; raw counts are always reported with the rate.

## 5. The 2017 benchmark (fixed now)

* **Seed 3101** (Phase 3 used 42). Scenarios are generated by code from the seed, written to `config/scenarios/dev2017.yaml`, and committed before the first run.
* **The six fault types:** segment level shift, payment failure, category price change, review collapse, seller delay, pipeline bug.
* **Size bands**, by the target's share of orders in the test period: large 5% or more, medium 1% to under 5%, small under 1%. The same bands are applied to the old 30-scenario benchmark.
* **Grid, 54 scenarios:**

| Fault type | Grid | Scenarios |
|---|---|---|
| segment level shift (state or category, alternating) | 3 sizes x 3 magnitudes | 9 |
| category price change | 3 sizes x 3 magnitudes | 9 |
| review collapse | 3 sizes x 3 magnitudes | 9 |
| payment failure | 4 payment types x 3 magnitudes | 12 |
| seller delay | 3 seller-state sizes x delays of 3, 7, 14 days | 9 |
| pipeline bug | {drop, duplicate} x shares 0.3, 0.6, 1.0 | 6 |
| **Total** | 27 + 12 + 9 + 6 | **54** |

  Magnitudes (share of rows removed, price cut, or review share set to 1) are **0.15, 0.30, 0.60**.
* **Duration:** 14 days for every fault except pipeline bug, which lasts 1 day.
* **Placement:** start dates are drawn by the seed from the allowed days only. The fault window plus its 7-day matching tail must not overlap the Black Friday event (2017-11-23 to 29) or the Christmas window (from 2017-12-20). So 14-day faults start between 2017-09-18 and 2017-11-02; pipeline bugs start between 2017-09-18 and 2017-11-14, or between 2017-11-30 and 2017-12-12. A direct consequence: **calendar handling (D) cannot affect any benchmark scenario by construction.**
* **Magnitude for stratification** is the *measured* relative change in the targeted segment (the total, when the target is not a monitored segment), as in Phase 3. The NFR-021 stratum is measured magnitude of 20% or more.

## 6. True-positive rule (fixed now)

* Let `effect_start` and `effect_end` be the first and last days on which the fault *measurably* changed an affected KPI of the **total** series (not the nominal dates).
* A scenario is **detected** if at least one **fault-caused** alert exists with a date in `[effect_start, effect_end + 7 days]`, on one of the scenario's affected KPIs, on **any** monitored series (total or any segment, daily or weekly). "Fault-caused" means the same alert (same date, KPI, granularity, dimension, segment) was **not** raised in the paired clean run of the same configuration. This is the Phase 3 definition, kept so numbers are comparable.
* **Targeted-series recall** is also reported: the alert must be on the targeted segment's own series (or on the total, for seller delay and pipeline bug).
* **Detection delay** is the first qualifying alert's date minus `effect_start`. Recall is also reported cumulatively at 0, 1, 3, 7 and 14 days after `effect_start`.
* **Precision** is fault-caused alerts on affected KPIs divided by all fault-caused alerts.
* Guard alerts (section 8) are reported in a **separate column**. Recall is given **with and without** them.

## 7. False-alarm accounting (fixed now)

* The headline false-alarm figure is **alarms per 30 clean days, counting every alert** in the clean run: guard alerts, `calendar_uncertain` alerts, and alerts that match a known event. Nothing is removed.
* The breakdown assigns each alarm to one cause, in this priority order: dataset cut-off (date after the last reliable day), calendar window, known event, GMV spike (KPI gmv, direction up), other.
* A **separate, non-exclusive** figure counts alarms that match any event in `config/known_events.yaml` ("alarms matching an unlabelled real event"). Those alarms are never moved into true positives.
* Both raw counts and rates are reported. Alarm-days (days with at least one alarm) are reported too.

## 8. Guard (change A, fixed now)

* **Volume-collapse rule:** a day is a collapse if total orders are below **35%** of the median total orders of the previous 28 days. The threshold is fixed now and not tuned.
* On a collapse day the system raises **one** alert, worded **"volume collapse (data feed or business)"**, with KPI `orders` and dimension `data_quality`, and **suppresses all other tests that day**, logging the reason. The wording deliberately does not claim the cause.
* A guard alert on a clean day **counts as a false alarm**.
* **Last reliable day (validity rule defined after diagnosis):** the last day before the terminal run of consecutive days, ending at the last day of the data, that are all collapse days under the rule above. Days after it are not tested and are logged as suppressed. The date is computed by code and recorded in `docs/DATA_PLAN.md`.
* The Phase 2 monitoring-window rule used a trailing 7-day mean, which lags and let the cut-off days in. It is corrected to a centred mean, and the EDA is re-run.

## 9. Other changes (fixed now)

* **B, log scale:** applied to **gmv only**. Skewness of every KPI's daily values in the fit period is reported, but no other KPI is transformed (no widening of scope). The interval is back-transformed.
* **C, share of total:** applies to `orders` and `gmv` only. A segment series (including pooled `__other__`) is tested as its share of the parent total; the **total stays level-based**. Ratio, rate and mean KPIs are unchanged, because they are not additive. Segments must still add up to totals (existing hard check). Related flags still group under one record (FR-033).
* **D, calendar:** windows come from the calendar alone: Christmas and New Year (20 December to 7 January), Carnival (the Saturday before Carnival Tuesday to Ash Wednesday), Black Friday week (the Thursday before to the Wednesday after Black Friday, the Friday after the fourth Thursday of November). Inside a window alerts are **not silenced** and **no post-holiday effect is fitted**. They are tagged `calendar_uncertain` and their severity is multiplied by **0.5**. Black Friday values are still removed from *training* (cleaning, as in Phase 3).
* **Investigation threshold:** severity of **1.0** (severity is relative deviation times log of the sample size). `calendar_uncertain` alerts are **not automatically below it**; they fall below it exactly when their raw severity is under 2.0.
* **Grouping inside a calendar window:** consecutive-day `calendar_uncertain` alerts of the same KPI and granularity are grouped (FR-033) into **one record** with its first date, last date and day list.
* **D cannot be measured on any Black Friday.** The 2017 Black Friday is excluded from development by the protocol, and the 2018 data ends in August, before Black Friday 2018. D's Black Friday behaviour is therefore **unevaluated**, and so is Carnival (2017 Carnival is in the fit period and 2018 Carnival is before the first evaluation day). Only the Christmas lull in December 2017 is observable, and only through the severity-ranked curve.

## 10. Keep or drop (fixed now; one iteration only)

Compare each configuration with `baseline-dev` on the same clean days and the same 54 scenarios.

* **B and C are kept only if** (clean alarms per 30 days fall by at least 25% relative **and** recall at 20% or more loses no more than 2 scenarios) **or** (recall at 20% or more rises by at least 3 scenarios **and** clean alarms per 30 days do not rise by more than 10%).
* **A and D are validity and labelling rules** and are kept regardless. They cannot show a benefit on 2017: the cut-off exists only in 2018, and D never changes the alarm count.
* Report for every comparison: raw clean-alarm counts, alarm-days, and a **paired comparison on the same days** (exact McNemar test on days with an alarm in one configuration and not the other) and a **paired comparison on the same scenarios** (exact McNemar test on detected / not detected). These tests are reported, not used as gates. Wilson 95% intervals accompany every recall.
* If a change does not help, it is dropped and the result is recorded. **No second tuning round.**

## 11. Operating curve (fixed now)

Recall at 20% or more against clean alarms per 30 days, for FDR level in {0.01, 0.02, 0.05, 0.10, 0.20} and minimum severity in {0, 0.5, 1.0, 2.0}. The headline uses FDR 0.05 with no severity cut, as in the baseline.

## 12. Known events (fixed now)

`config/known_events.yaml`, committed with this document: the Brazilian truckers' strike (2018-05-21 to 2018-05-31, all KPIs) and the five days on which Brazil played in the 2018 World Cup (17 June, 22 June, 27 June, 2 July, 6 July; `orders` and `gmv` only). No event may be added after the 2018 run starts.

## 13. Final evaluation (fixed now)

1. Freeze the configuration and commit it.
2. Run the 2018 evaluation **once**, labelled "post-diagnosis, not held-out".
3. Run the original 30-scenario benchmark **once** with the frozen configuration, same label.
4. If anything fails afterwards, **do not iterate**; report it.
5. All numbers are produced by the harness and logged to MLflow with the git SHA, data hash, detector version, scenario-file hash and seed. No result is typed into a document by hand.

## 15. Deviations and clarifications

Recorded with the date and reason, before the affected run.

* **2026-10-26, strict recall (owner instruction).** The strict figure is defined as: a fault-caused alert on an affected KPI, on the **targeted segment's own series, within 3 days of the first affected day**. For a monitored dimension the own series is the target segment's series, or the dimension's pooled `__other__` series when the segment is pooled for that KPI; for faults not aimed at a monitored dimension (seller delay, pipeline bug) it is the total series. A flagged series counts whether it is an alert's headline or one of its related segments. This **replaces** the "targeted-series recall" bullet in section 6, which used the 7-day tail. The lenient figure keeps the Phase 3 definition.
* **2026-10-26, which recall is compared with NFR-021.** The **lenient** figure, because the baseline was measured that way and a comparison must be like for like. The strict figure is shown beside it as the more demanding reading, with its own Wilson interval.
* **2026-10-26, what "exactly" means for the golden tests.** Running the capture twice showed that DuckDB's multi-threaded floating-point sums differ in the last digit (about 1 part in 10^16) between runs. Every **discrete** value (alert keys, counts, recall, delays, booleans) must match exactly; floats are compared to a relative 1e-9. The real-data golden compares alert keys and counts exactly and ratios of integers exactly.
* **2026-10-26, golden regression runs on 2018.** The check that all flags off reproduces the Phase 3 baseline on the real 2018 data is a **regression check**, not an evaluation: it reproduces numbers that are already known and its output is asserted equal to them, so it creates no new information and nothing is tuned from it. It was run once at the end of step 1 and **passed** (9/16, 9.26 false alarms per 30 days, 75 alerts, every scenario outcome identical; 16 minutes). It is run again before the final run if code on the baseline path changed. It is separate from the one final evaluation run of section 13.
* **2026-10-26, seller-delay start dates.** A delay moves deliveries later, so the measurable effect extends beyond the 14-day window by the delay. The placement rule is unchanged (fault effect plus the 7-day tail must not overlap Black Friday week or the Christmas window); applied to seller delay it narrows the allowed start range by the delay length.
* **2026-10-26, reporting helpers written in step 1.** `ds/calendar.py` (calendar window definitions, also used to place faults) and `evaluation/breakdown.py` (`last_reliable_day`, the false-alarm classifier, the known-event matcher) are reporting utilities needed by E and by the benchmark. They change no alert. The guard behaviour (A), the log scale (B), the share test (C) and the severity tagging (D) are **not yet written**, and the configuration flags for them refuse to switch on.
* **2026-10-26, event dates and timezones.** Events are compared as plain **Brazilian local calendar dates**. Olist timestamps are naive local time with no timezone, and nothing in the date path converts one. The matcher rejects datetimes and timezone-aware values instead of silently shifting them (tested, including that a 02:30 UTC instant on 18 June is the 17 June local date).
* **2026-10-26, development baseline.** `baseline-dev` is the Phase 3 detector refitted on the fit period only (2017-04-26 to 2017-08-27), written to `config/detector_dev2017_baseline.json`. AutoARIMA is skipped in this refit because it is report-only and never selectable. Calibration therefore comes from about 8 weeks, which makes the intervals conservative (calibrated coverage 91% to 99% on the second half of the fit period).

* **2026-10-26, how representative the 2017 development set is (owner-confirmed).** The 2017 development data is **harder and less representative** than 2018: the fit period is only about 4 months, the business was growing quickly, and calibration comes from about 8 weeks. Deltas measured on 2017 **may not transfer to 2018**. This is a limit of the protocol, stated before any change was measured.
* **2026-10-26, zero-effect scenarios.** Six of the 54 scenarios have a measured effect of about 0% (targets with almost no orders in the test period). They are **kept and reported as they are**; none is swapped or dropped. They fall in the under-10% stratum and do not affect the NFR-021 figure.
* **2026-10-26, pre-run check for change A (finding, recorded before the evaluation).** With the pre-registered rule unchanged (below 35% of the median of the previous 28 days), the guard fires on **one** day of the 2017 test period: **Sunday 2017-12-24** (59 orders, 27% of the 28-day median of 218.5). It does **not** fire on 25 December (41%) or on any other test day. It also fires on 2017-06-21, which is in the fit period and is never tested. 24 December is a legitimate holiday day, so under the pre-registered accounting this alert is **one false alarm**. **No calendar exemption is added and the 35% is not tuned.** The finding is reported with the change A results.
* **2026-10-26, rule and date of the last reliable day.** The rule (section 8) and its computed value, **2018-08-24**, are both recorded in `docs/DATA_PLAN.md`. The date lives in `config/detection.yaml` (`feed_guard.data_end`) and `python -m ds.feed_guard --check` recomputes it from the warehouse and fails if they differ.
* **2026-10-26, test-day denominator when days are silently suppressed.** Days past the last reliable day are not tested and raise no alert, so they are **not** counted as clean tested days: the false-alarm denominator is the clean days minus the silently suppressed days. Collapse days stay in the denominator, because the guard raises an alert on them. The raw counts are always reported too. This affects the 2018 runs only (7 suppressed days, 25 to 31 August); the 2017 runs have none.
* **2026-10-26, guard alerts and strict recall.** A guard alert is a total-level data-quality alert, so it counts toward strict recall only for faults whose target is the total series (seller delay, pipeline bug), and never for segment faults. Recall is reported with and without guard alerts.
* **2026-10-26, what D changes about the alarm count (clarification of sections 9 and 10).** Tagging and the severity multiplier never change how many alerts are raised. The grouping of consecutive-day `calendar_uncertain` alerts into one record (section 9) does reduce the number of **records**. Both are reported: the headline false-alarm figure stays the **number of alerts before calendar grouping**, so configurations remain comparable, and the grouped record count is shown beside it.
* **2026-10-26, change A, measured (run on commit `ef5203c`, clean tree).** Reported with the other changes in section 14. Findings recorded here at the time: the guard fired on exactly one clean day, 2017-12-24, and replaced the 10 statistical alerts of that day with one guard alert, so alerts fell from 62 to 53 while alarm-days stayed at 31; one scenario (S51, a 100% one-day drop) is detected only through a guard alert.
* **2026-10-26, how B was implemented (before its evaluation).** `log1p` is applied to **GMV only**, to every GMV series that stays level-based. The model is fitted on `log1p(y)`; the calibration factor, coverage, error and the z-score are computed **in log space**, and the expected value and interval are reported back in BRL (`expm1`), so the interval is asymmetric (wider above). GMV series form their own detector group (`volume_log1p|daily` and `|weekly`), so model choice and calibration are made separately from `orders`. The MASE scale of those series is also taken on the log scale. The detector file records `transforms` and `share_kpis`, and the evaluation refuses to run if the detector and the flags disagree. Skewness of every KPI's daily total in the fit period is stored in the detector file.
* **2026-10-26, how C was implemented (before its evaluation).** For `orders` and `gmv`, every segment series (including pooled `__other__`) is replaced by `segment numerator / total numerator` on the same day (daily series) or the same week (weekly series); the **total stays level-based**. Series ids are unchanged. Share series form their own detector group (`share|daily`, `share|weekly`), with model choice and calibration of their own. The minimum-sample gate and the alert direction (both) are unchanged. A share is undefined when the total is zero and is then never tested. Because a fault in one segment also moves every other segment's share and the total, more series change per scenario, so scenario runs re-forecast more series. Ratio, rate and mean KPIs keep the level-based test. Related flags still group under one record.
* **2026-10-26, how D was implemented (before its evaluation).** Alerts dated inside a calendar window get `calendar_uncertain = true`, the window name, and **severity x 0.5**; nothing is silenced. With D on, known-event days (Black Friday) are **tested** instead of silenced; their values are still removed from **training**. The grouping of consecutive-day calendar-uncertain alerts into one record (FR-033 across days) is the pure function `group_calendar_alerts`, applied in the **evaluation and storage layer**; `detect_range` itself still returns the per-day alerts. The evaluation reports the alerts before grouping (the headline), the records after grouping, and how many records are at or above the investigation threshold of 1.0. Recall cannot change under D, because no benchmark scenario overlaps a calendar window by construction.
* **2026-10-26, Phase 2 window rule corrected.** The EDA now uses a centred 7-day mean. Result and its limits are in `docs/DATA_PLAN.md`: both ends move three days earlier (2017-01-23 to 2018-08-28) and the first collapse days are still inside it. `config/detection.yaml` keeps the original window so the Phase 3 baseline stays reproducible.

## 16. Alternatives considered

* **Go straight to Phase 4.** Rejected by the owner for now; the root-cause agent depends on alert quality.
* **Tune on 2018.** Rejected: the numbers would stop meaning anything.
* **Re-label the strike alarms as true positives.** Rejected: they stay false alarms in the headline.
* **Silent suppression on a collapse day.** Rejected: it would lose the only signal for a total feed failure.
* **Add a seller-state dimension.** Deferred.

## 17. Consequences

* If NFR-021 is still not met after this round, that is reported plainly and no further tuning happens in Phase 3.
* The 2017 benchmark and its protocol become the standard development benchmark. A genuinely held-out check needs data the project has not looked at; none exists in this dataset after August 2018.
